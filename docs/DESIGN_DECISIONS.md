# 设计决策记录（ADR）

> 记录关键取舍，方便面试时讲「为什么这么做」，也方便未来自己回看。

## ADR-1 感知用「截屏 + OCR」，不用 hook / 协议 / UIA

**背景**：微信没有公开 API；网页协议已停服；hook/注入封号风险高；微信 4.x 自绘导致 UIA 控件树不可用。
**决策**：截屏 + OCR + 键鼠模拟，与读屏软件同类操作。
**代价**：依赖 UI 布局与配色，改版需重新标定；OCR 有延迟（用帧缓存缓解）。
**替代方案为何不选**：hook 方案违反协议、封号风险；UIA 在新版微信上拿不到控件。

## ADR-2 截图用 PrintWindow，而不是 DDA/GDI

**背景**：微信窗口自绘在 GPU 画布上，GDI 截屏可能黑屏；DDA 只能截可见屏幕，窗口被遮挡时截到别的程序。
**决策**：`PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)`，实测像素与屏幕一致、遮挡也能截。
**代价**：个别窗口返回空白帧（已加 3 次重试 + 空白检测）；仍依赖窗口句柄有效。

## ADR-3 气泡配色自动标定，而不是写死

**背景**：微信 4.x 气泡绿从 RGB(149,236,105) 变成 RGB(157,242,159)，深色主题更不同；写死必错。
**决策**：几何自举（短消息左右留白差异 → 侧别标签）+ 颜色聚类（彩色=我、比背景亮=对方），按背景色做主题指纹缓存。
**代价**：浅色主题下「白气泡 vs 浅灰背景」对比度低，需要邻域投票 + UNKNOWN 语义（判不出来就不触发）。

## ADR-4 触发用「尾部序列状态机」，而不是消息指纹集合

**背景**：旧实现用 `(speaker,text)` 集合去重 → 重复内容永久失效、滚动误触发、启动回旧消息。
**决策**：状态机 + 尾部序列「追加判定」：只有**上一帧末条仍出现在新帧非末条里**才算追加；
同气泡多行合并用气泡左右边界一致性判断。
**代价**：极端滚动/OCR 错字时可能漏触发（宁漏勿错）。

## ADR-5 记忆用「结构化事实 + RAG」，而不是把知识微调进模型

**背景**：聊天经历是持续增长、会变化、需要溯源和删除的；微调无法更新且不可解释。
**决策**：L0-L5 分层；事实卡带证据/有效期/置信度，同 key 自动 supersede；检索 = 相关性 + 时效 + 置信度 + 向量召回。
**代价**：需要 LLM 抽取 + 人工抽查；抽取质量决定记忆质量。

## ADR-6 风格用 LoRA，而不是只靠 prompt

**背景**：prompt 能描述风格，但短句、标点、口头禅这类「手感」很难写全；RAG 解决不了口吻。
**决策**：知识走记忆，口吻走 3B QLoRA（只存 adapter）；prompt 里仍保留风格规则与 few-shot 做兜底。
**代价**：8GB 显存下只能 3B；需要真实数据才有实际价值；训练/评测需分两段跑（显存争用）。

## ADR-7 默认 dry-run，三级发送模式

**背景**：一旦自动发送，最危险的是「把回复打进别的程序」和「说错话」。
**决策**：`dry_run`（默认只预览）/ `review`（逐条确认）/ `send`；发送前校验前台窗口，剪贴板保存恢复，
模型输出做出口清洗与金钱话题拦截。
**代价**：全自动体验打折；但安全优先。

## ADR-8 评测拆成「生成」与「盲评」两段

**背景**：8GB 显存同时放 3B 生成模型 + 本地 7B 评委 → 显存溢出/Ollama 卡死。
**决策**：先生成并把回复落盘（`ab_report.json`），进程退出释放显存，再跑评委脚本（`judge_replies.py`）；
评委交换 A/B 位置，两次一致才判胜，抵消位置偏差。
**代价**：多一步操作；换来稳定的本地评测流程。

## ADR-9 trace 落 JSONL 而不是引入重观测栈

**背景**：个人项目，需要的是「这一轮卡在哪」，而不是分布式链路追踪。
**决策**：轻量 `Tracer`，每轮记录 perceive/generate/send/tick 的毫秒与动作，写 `data/trace/*.jsonl`。
**代价**：无指标聚合/可视化（后续可接 OpenTelemetry/Langfuse）。

## ADR-10 在线用 7B + 记忆闸门，3B LoRA 只做离线风格工具

**背景**：真实数据训出 3B LoRA 后，想让它同时承载「画像 + 层级记忆」甚至承担两段式改写。
实测两轮后否定：
1. 3B LoRA + 长 prompt（画像+77 条事实）：复读口头禅/答非所问；按推理 prompt 重训（loss 0.32）
   反而学会**复述 system 里的记忆与画像**；
2. 两段式（7B 草稿 → 3B 改写）：3B 把草稿当背景噪声，丢内容（有的/我胖了/128GB），
   7B 盲评草稿 6 : 改写 1 : 平 1。

**决策**：
- 在线主链路 = **7B（或云端）+ 自动画像 + 记忆闸门**（
eeds_memory() 只在提问/约时间/回忆词注入）；
- **3B LoRA 只做离线风格改写/降本**，输出要再过 7B 质检，不参与在线自动回复；
- 两段式实现保留在 gent/two_stage.py，作为负结果与后续 rewriter 训练的起点。

**代价**：在线成本更高（7B 慢于 3B）；换来内容正确性与可解释性。
**后续（已试）**：用 7B 批量生成 500 条草稿训练 rewriter，实测两版都以失败告终：
v1 loss 1.16、v2（极简 prompt/2 epochs）loss 0.86，held-out 保真度仍 ≈0，只有短句风格被学会；
盲评甚至偏好 rewriter（46.7% 胜），说明**风格评委发现不了内容丢失**。已在 TwoStageGenerator
加 fidelity 兜底（2-gram 重叠 <0.15 退回草稿），避免风格洗白。
